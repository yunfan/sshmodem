# 技术决策记录

每条记录：**决定**、**理由**、**放弃了什么**。
新决定追加在末尾，不改旧条目；改变主意时新增一条并注明取代了哪条。

日期格式 YYYY-MM-DD。状态：`已定` / `待确认` / `已取代`。

## D1 · 名字叫 smodem
**2026-09-29 · 已定**

SOCKS + modem。延续 XMODEM/YMODEM/ZMODEM 的命名传统，一眼看出"在一条线上跑协议"。
远端命令固定写作 `smodem serve`。

---

## D2 · 不做重传、不做序号、不做 ACK
**2026-09-29 · 已定**

载体是 SSH over TCP，已经可靠有序，MAC 也已校验完整性。
在可靠通道上再叠一层 ARQ 是纯粹的重复劳动，还会引入一整套超时与重传定时器要调。

**放弃**：无法在不可靠载体（裸串口、无线电）上直接使用。
这不是本工具的场景——本工具的场景是跳板机。

---

## D3 · 每帧不带 magic，也不带 CRC
**2026-09-29 · 已定**

帧边界由 `length` 唯一确定，可靠有序的载体上不会失步。
启动阶段的垃圾用一次性引导序列 `~~SMODEM/1~~` 清理。

真正的风险不是随机比特翻转，而是**通道不透明**（pty 的 `ONLCR` 插入字节）。
这种错误一旦发生就是**全局性的**，逐帧 CRC 只能在每一帧上重复报告同一个问题，
不如握手时用一次探针把它彻底查清楚（D4）。

**放弃**：帧层面的自纠错能力。出错即断开整个会话，靠上层重连。
可靠载体上出现这种错误只可能是实现 bug，继续跑只会扩散错误。

---

## D4 · 通道透明性自检（PROBE）
**2026-09-29 · 部分取代（探测细节见 D19）**

握手后、承载数据前，两个方向各发一次 272 字节固定图案
（256 个全值 + 16 个终端陷阱字节），对端回 CRC32 与长度。

这是本工具相对"直接上 SOCKS over stdio"的核心增量。没有它，
pty 的 `ONLCR` 会让数据**静默损坏**，表现为"偶尔连不上、偶尔乱码"，
用户根本无从诊断。有了它，失败发生在第一秒，且错误信息直接指出根因
（长度变长 = 有东西在插字节；长度变短 = 有东西在吞字节）。

**放弃**：272 字节 × 2 的启动开销和一个 RTT。完全可以接受。

---

## D5 · 引导失败时把丢弃的垃圾打到 stderr
**2026-09-29 · 已定**

引导阶段丢弃的字节留最后 4 KiB，超时失败时原样打印。

跳板机场景下失败的真正原因几乎总在那段文本里：`Permission denied`、
`command not found`、`Host key verification failed`。
不打出来，用户面对的就是一个沉默的超时；打出来，一眼就知道该改什么。

---

## D6 · 双层窗口 + 停止读取式背压
**2026-09-29 · 已定**

流窗口 128 KiB，会话窗口 2 MiB，两层同时扣减。
窗口不足时**停止从源 socket 读取**，而不是读进来缓冲。

这样背压一路顶到 TCP 源头，由内核接收缓冲承担，进程内存与流量无关。
只做单层流窗口的话，N 条流的最坏内存是 N × 128 KiB，会失控；
只做会话窗口的话，单条流能饿死其它所有流。

**放弃**：实现上多一个计数器和一类窗口帧。收益远大于成本。

---

## D7 · 出站 round-robin，控制帧优先
**2026-09-29 · 已定**

每条流一个待发队列，写管道时轮转取帧；控制帧走独立优先队列，不受窗口约束。

单一 FIFO 会让一个大文件下载把队列占满，饿死嵌套 SSH 和终端交互——
这是用户能直接感觉到的"卡"。控制帧不优先则会死锁：窗口更新帧被数据堵住，
数据又在等窗口更新。

---

## D8 · 地址块照抄 RFC 1928（端口大端），帧头小端
**2026-09-29 · 已定**

帧头字段一律小端；地址块原样使用 SOCKS5 编码，端口保持大端。

字节序不统一看着别扭，但换来的是：SOCKS5 请求里的地址字节可以**原样搬运**进
`OPEN` 帧，不做任何解析和重编码。少一次转换就少一类 bug，
错误码也同理（`OPEN_ERR` 的 payload 就是 SOCKS5 的 REP 码，三层之间零翻译）。

---

## D9 · 域名在远端解析
**2026-09-29 · 已定**

`ATYP=0x03` 的域名原样送到远端。这是隧道的意义（用远端的网络视角看世界），
顺带消除 DNS 泄漏。

---

## D10 · 单线程 poll(2) 事件循环
**2026-09-29 · 已定**

所有流共享一条出站管道，这是天然的串行点。多线程只会为抢这个点加锁，
换不来吞吐，却换来一整类竞态 bug。

先用 `poll(2)` 而不是 `epoll`：POSIX 通用（Linux/macOS/BSD 一份代码），
SOCKS 代理的并发量级（几百条）下 O(n) 扫描不是瓶颈。
`io/poller.zig` 是一层薄封装，日后有实测瓶颈可以替换成 epoll/kqueue 而不动上层。

---

## D11 · 协议自身不做加密和认证
**2026-09-29 · 已定**

完全依赖载体。跑在 SSH 上时机密性、完整性、身份认证都已具备，
再叠一层是重复劳动，而且自己实现加密更容易出错。

**代价**：不得在裸 TCP / 裸串口上承载敏感流量。文档明确写出这条限制。
本地监听默认绑 `127.0.0.1`；绑到其它地址等于把无认证代理暴露给整个网络，
实现必须对此告警。

---

## D12 · 默认 ReleaseSafe + baseline CPU + 静态 musl
**2026-09-29 · 已定**

用户明确要求"不要用 debug 编译，要出基线版本"。落实为三条：

- `ReleaseSafe` 而非 `ReleaseFast`：这是处理不可信网络输入的程序，
  保留边界检查与整数溢出检查。真有热点再针对性优化，不整体降级。
- `-Dcpu=baseline`：跳板机 CPU 可能很老，不赌目标机的指令集扩展。
- 静态链接 musl：远端二进制要能丢到任何一台 Linux 直接跑，不依赖对方 glibc 版本。

`zig build` 默认就是这套参数，Debug 产物不进构建目标。

## D13 · v1 不做 UDP ASSOCIATE
**2026-09-29 · 已取代（见 D16）**

`caps` 位 0 保留，v1 置 0，收到该命令回 `REP=0x07`。

浏览器与绝大多数 TCP 应用不需要它；DNS 走 `ATYP=0x03` 域名模式由远端解析即可。
要做的话需新增 `UDP_OPEN`/`UDP_DATA` 两个帧类型、每个 datagram 带地址头、
以及 UDP 关联的生命周期绑定——独立且不小的一块，适合单独立项。

**用户答复**：v1 就要做。见 D16。

## D14 · v1 不做转义编码
**2026-09-29 · 已取代（见 D17）**

pty 用 `cfmakeraw` 切成 raw 即可 8-bit clean，不需要转义。
只有中间夹着无法控制的设备（真串口、console server、`screen`）时才需要。
v1 的做法是探针明确报错并给出修复建议，而不是静默传错数据。

**用户答复**：中间确实有管不了的设备。见 D17。

---

## D15 · v1 不做会话恢复，但自动重启传输
**2026-09-29 · 已定**

ssh 断线时，已建立的流全部失效（SOCKS5 客户端会自行重试），
本地端自动重新拉起 ssh 并重建会话。

真正的会话恢复需要序号 + 发送侧重传缓冲，那就是把 D2 否掉的 ARQ 又请回来了。
自动重启拿到 90% 的价值，只花 10% 的成本。`caps` 位 2 为将来留好位置。

---

## D16 · v1 实现 SOCKS5 UDP ASSOCIATE
**2026-09-29 · 已定，取代 D13**

用户明确要求 v1 就要有 UDP。新增 `UDP_OPEN` / `UDP_OPEN_OK` / `UDP_OPEN_ERR` /
`UDP_DATA` 四个帧，`caps` 位 0 置 1。

**UDP 关联寄生在一条 TCP 流上**：SOCKS5 本来就规定 TCP 控制连接一断关联即结束，
所以 UDP 帧的 `stream_id` 直接用那条 TCP 流的 id。生命周期天然一致，
不需要额外的关联表，也不会泄漏 socket。这是"约定大于配置"最划算的一次应用。

主要价值是 DNS 走 UDP、QUIC、以及少数把 UDP 当传输的客户端。

**代价**：协议面和测试面各多一块；UDP 中继必须做来源校验，否则就是一个
能被拿去做反射放大的开放中继（协议 §9.4，这是必须项不是可选项）。

## D17 · 实现传输编码层 RAW / ESC / B64
**2026-09-29 · 已定，取代 D14**

用户确认中间有管不了的设备（真串口、console server 一类），`cfmakeraw` 救不了。
因此在帧层之下加一层传输编码，三档：

| 编码 | 开销 | 前提 |
|---|---|---|
| `RAW` | 0% | 8-bit clean |
| `ESC` | ~6% | 8 位能过，吞/改控制字符 |
| `B64` | 33% | 只有可打印 ASCII 能过 |

**分层是这个决定的重点**：编码层紧贴 fd，帧层及以上**完全看不见它**。
线有多烂是编码层一个人的事，mux、socks5、local、serve 的代码一行都不用变。

两个方向**各自独立**协商——上行经过 pty 而下行是管道这种情况很常见，
没理由让好的那个方向陪着降档。

**代价**：多一个带状态的增量解码器（转义序列、Base64 四元组都可能跨 `read()` 分片），
这是最需要被测狠的一层，测试策略见 design.md §7.1–7.2。

## D18 · 标记字节用 `%`，绝对不用 `~`
**2026-09-29 · 已定**

原设计的引导序列是 `~~SMODEM/1~~`，**这是个真 bug**：`~` 是 ssh 客户端自己的
escape 字符，只要分配了 pty，行首的 `~~` 就会被 ssh **吞成一个 `~`**，
而 `~.` 会直接断开连接。这个破坏发生在 ssh 客户端进程内部，
与远端的 `termios` 设置无关，`cfmakeraw` 完全救不了。

改用 `%`（0x25），并把 SYNC 改为 `%%SMODEM/1%%`。选它的理由逐条排除过：

- 可打印 ASCII，任何链路都能过，出问题时人眼能在日志里认出来；
- 不是 ssh 的 escape（`~`）；
- 不是 shell 元字符（`$` `` ` `` `"` `'` `\` `!` 全部排除，`!` 因 bash 历史展开也排除）；
- 不在 Base64 字母表内，能和 Base64 数据区分。

这条记下来是因为它是**设计阶段捡回来的一条命**：如果照原设计写完，
表现会是"管道模式一切正常，一上 pty 就永远握手超时"，
而且查起来会往 termios 方向查，根本查不到 ssh 客户端头上。

## D19 · 探针改为逐级降档 + 回传原始字节
**2026-09-29 · 已定，取代 D4 的探测细节**

D4 原设计是一轮探针、回传 CRC32 与长度。有了编码层之后不够用了，改成：

```
Round 0：用 RAW 发探针 → 一致？ → 选 RAW
Round 1：用 ESC 发探针 → 一致？ → 选 ESC
否则                              选 B64（握手已证明它能过，不必再测）
```

`PROBE_RESULT` **回传收到的全部原始字节**（经 B64 安全带回），不只是 CRC32。
多花 363 字节，换来发送方能**逐字节比对**，把根因直接说出来：

```
first difference at offset 10:
  sent     ... 08 09 0A 0B ...
  received ... 08 09 0D 0A ...
                     ^^ 0x0A became 0x0D 0x0A
likely cause: ONLCR on a pty
```

只有 CRC 的话，用户只能得到"校验错误"四个字，然后自己去猜。
在跳板机这种没法随便调试的环境里，这个差别就是能不能用的差别。

探针边界靠 `%%` 判定（见 D20），图案里 `0x25` 只出现一次且两侧不同，
所以不含 `%%`，判定成立。

## D20 · `%%` 永不自然出现，作为全局同步标记
**2026-09-29 · 已定**

这是编码层设计出来的一条不变量：

> 在 RAW 以外的任何编码下，`%%` 永不在数据中自然出现。

- B64：Base64 字母表不含 `%`；
- ESC：转义序列是 `0x25, (b XOR 0x40)`，第二字节要等于 `0x25` 需要 `b = 0x65`（`'e'`），
  而 `'e'` 不在转义集合里，所以永远产生不出第二个 `%`。

有了它，`%%` 就能同时充当：引导序列的一部分、B64 帧的起始标记、
探针裸段的结束边界。三处复用同一个机制，不用再发明三套定界规则。

RAW 模式下不变量不成立（数据里当然可能有 `%%`），但 RAW 模式意味着线是干净的，
不需要重同步——逻辑自洽。

**必须有测试守住这条不变量**（穷举 + 随机数据断言输出不含 `%%`）。
它一旦塌了，引导和探针边界会同时错，而且错得很隐蔽。

## D21 · 远端二进制部署不做自动化
**2026-09-29 · 已定**

用户选择自己 `scp`。工具只约定"远端 PATH 里有 `smodem`"，
不提供自动上传，也不做版本探测。

`zig build release` 产出静态链接 musl、baseline 指令集的二进制，
体积控制在 1 MiB 量级，丢到任何一台 Linux 跳板机上都能直接跑。
usage.md 给出 `scp` 与 `cat | ssh` 两条现成命令。

**放弃**：一条命令开箱即用的体验。换来的是行为完全可预期——
工具不会在用户不知情的时候往跳板机上写东西。跳板机往往是受管控的机器，
这个取舍在这种环境里是对的。
